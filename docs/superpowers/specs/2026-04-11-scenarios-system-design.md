# Система сценариев: официальные + пользовательские

**Дата:** 2026-04-11  
**Статус:** утверждено пользователем для фиксации в спецификации

## Контекст

Нужно добавить в игру поддержку набора сценариев (около 20), где каждый сценарий задает собственную расстановку объектов стола: ландшафт, эфирные вихри, кристаллы на вихрях, токены, артефакты, пленники и другие элементы, входящие в состояние поля.  
Также сценарий должен задавать ориентацию поля (горизонтально/вертикально), где на текущем этапе это трактуется как поворот поля.

Пользовательский запрос:

- иметь предустановленные (официальные) сценарии;
- иметь пользовательские сценарии;
- хранить пользовательские сценарии и локально, и в виде JSON-файлов (экспорт/импорт);
- применять сценарий как полный снимок стола;
- в мультиплеере разрешить применение сценария любому игроку;
- создавать пользовательский сценарий через мини-редактор с обязательными полями.

## Цели

1. Поддержать официальный каталог сценариев и пользовательские сценарии в одном UX.
2. Применять сценарий как полный board snapshot без отдельной второй системы состояния.
3. Поддержать локальное хранение пользовательских сценариев + экспорт/импорт JSON.
4. Добавить мини-редактор сценария (обязательные метаданные при создании).
5. Сохранять/восстанавливать ориентацию поля (поворот) как часть сценария.
6. Обеспечить корректное поведение в соло и мультиплеере.

## Не цели (v1)

- Поэлементный редактор сценариев (ручное редактирование конкретных сущностей внутри сценария).
- Серверная библиотека сценариев и учетные записи.
- Ролевая модель в мультиплеере (кто может применять сценарий) — в v1 разрешено всем.
- Новая отдельная доменная модель поля, дублирующая существующий board snapshot.

## Выбранный подход

Подход: **единый формат сценария на базе существующего board snapshot + метаданные**.

Причины выбора:

- в проекте уже есть проверяемый snapshot-формат и `capture/apply` поток;
- это снижает риск регрессий и стоимость внедрения;
- одинаково подходит для официальных и пользовательских сценариев;
- проще поддерживать совместимость через версионирование документа сценария.

## Модель данных сценария

Документ сценария (`ScenarioDocument`) содержит:

- `id`: стабильный идентификатор;
- `version`: версия формата сценариев;
- `kind`: `official | custom`;
- `meta`:
  - `name` (обязательное),
  - `description` (обязательное),
  - `tags[]` (обязательное, допускается пустой массив),
  - `difficulty` (обязательное),
  - `author` (опционально),
  - `updatedAt` (опционально/системно);
- `boardOrientation`: `horizontal | vertical` (семантика: поворот поля);
- `snapshot`: полный сериализуемый снимок стола в существующем формате;
- `flags` (опционально): служебные флаги для UI/совместимости.

### Семантика ориентации и связь с runtime

- `horizontal`/`vertical` задают именно **абсолютную ориентацию стола** как пресет поворота поля (не относительную к игроку).
- На уровне runtime `boardOrientation` маппится в фиксированное значение поворота поля (например, 0deg для `horizontal` и 90deg для `vertical`; точные градусы закрепляются в implementation plan).
- В текущей модели `snapshot` (`SerializedBoardStateV1`) не содержит отдельного поля ориентации, поэтому при применении сценария ориентация выставляется отдельным шагом из `ScenarioDocument`.

## UX и пользовательские потоки

### 1) Каталог сценариев

В меню добавляется пункт `Сценарии` с двумя вкладками:

- `Официальные`;
- `Мои`.

Карточка сценария показывает: имя, описание, теги, сложность, дату изменения.

### 2) Применение сценария

- Действие `Применить`.
- Подтверждение: сценарий полностью заменит текущее состояние стола.
- После подтверждения:
  1. полностью валидируется документ сценария и вложенный `snapshot`;
  2. применяется `snapshot`;
  3. выставляется `boardOrientation`.

### 3) Создание пользовательского сценария

- Кнопка `Создать из текущего стола`.
- Открывается мини-редактор с обязательными полями:
  - имя,
  - описание,
  - теги,
  - сложность.
- После сохранения сценарий попадает в раздел `Мои`.

### 4) Управление пользовательскими сценариями

- `Редактировать метаданные`;
- `Дублировать`;
- `Удалить`;
- `Экспорт JSON`;
- `Импорт JSON`.

Хранение:

- основное быстрое хранение в `localStorage`;
- экспорт/импорт через JSON-файлы для переноса/бэкапа.

## Архитектурные изменения (модули)

Предлагаемая новая подсистема:

- `src/scenarios/types.ts` — типы документа сценария и метаданных;
- `src/scenarios/schema.ts` — runtime-валидация/проверка версии;
- `src/scenarios/store.ts` — `localStorage` CRUD для custom сценариев;
- `src/scenarios/official.ts` — загрузка официальных сценариев из статических JSON;
- `src/scenarios/io.ts` — импорт/экспорт JSON (с проверками и ошибками);
- `src/scenarios/apply.ts` — единая функция применения сценария:
  - применить snapshot,
  - выставить ориентацию поля,
  - инициировать синхронизацию изменения.

UI:

- новая панель/модалка `Сценарии` с вкладками, карточками и действиями управления;
- форма мини-редактора для обязательных полей при создании.

## Data flow

### Создание сценария

1. Пользователь открывает `Создать из текущего стола`.
2. Заполняет обязательные поля метаданных.
3. Система делает `captureBoardSnapshot()`.
4. Формируется `ScenarioDocument`.
5. Выполняется валидация.
6. Сценарий сохраняется в custom-store (`localStorage`).

### Применение сценария

1. Пользователь выбирает сценарий в каталоге.
2. Система валидирует документ и вложенный `snapshot` до любой мутации состояния.
3. Применяет `snapshot` через существующий pipeline.
4. Применяет `boardOrientation`.
5. Публикует изменение в board sync (для MP).

### Импорт/экспорт

- Импорт: чтение JSON -> проверка схемы/версии -> разрешение коллизий `id` -> сохранение.
- Экспорт: сериализация выбранного сценария в JSON-файл.

## Мультиплеер

В рамках утвержденного решения:

- сценарий может применить любой игрок;
- применение сценария идет как обычное изменение board state;
- состояние после применения синхронизируется всем участникам комнаты.
- ориентация сценария считается общей для комнаты (абсолютный поворот поля), а не персональной настройкой клиента.
- текущая seat-коррекция вида (логика противоположного места за столом) применяется поверх общей ориентации как локальный визуальный слой и не меняет сохраненный документ сценария.

Опционально для UX v1: системный toast/событие "Игрок X применил сценарий Y".

## Обработка ошибок

- Невалидный JSON при импорте -> понятное сообщение, без применения.
- Неподдерживаемая версия сценария -> отказ с объяснением.
- Несовместимость по версиям (`ScenarioDocument.version` или `snapshot.v`) -> отказ без частичного применения.
- Коллизия `id` -> выбор: заменить или сохранить как копию.
- Переполнение `localStorage` -> подсказка по очистке/экспорту.
- Любая ошибка применения -> атомарный отказ (текущий стол не должен оказаться в частично примененном состоянии).

## Тестирование

### Unit

- валидация документа сценария;
- совместимость/миграции версий (при появлении новых версий);
- CRUD custom-store;
- импорт/экспорт с ошибками.

### Integration

- создать сценарий из текущего стола -> перезагрузить страницу -> сценарий доступен и применим;
- применение сценария корректно восстанавливает полный snapshot и ориентацию.

### Multiplayer smoke

- клиент A применяет сценарий;
- клиент B получает идентичное состояние поля без ручных действий.

### Regression

- существующий board sync не деградирует;
- существующие механики взаимодействия со столом вне сценариев не ломаются.

## Риски

- Сильная связность с форматом snapshot: изменения snapshot потребуют сопровождения сценариев.
- Большие сценарии могут упираться в ограничения `localStorage`.
- Разрешение применения всем игрокам в MP может вызывать случайные перезаписи состояния.

## Критерии готовности (DoD)

1. В UI есть каталог сценариев с вкладками `Официальные` и `Мои`.
2. Пользователь может создать сценарий из текущего стола через мини-редактор обязательных полей.
3. Пользовательские сценарии сохраняются в `localStorage`.
4. Работают экспорт и импорт пользовательского сценария в JSON.
5. Применение сценария восстанавливает полный state и ориентацию поля.
6. В MP применение сценария одним клиентом синхронизируется остальным.
