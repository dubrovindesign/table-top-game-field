# Кошелёк кристаллов — синхронизация в мультиплеере

**Дата:** 2026-04-11  
**Статус:** утверждено для реализации (технический дизайн)

## Контекст

Виджет `CrystalWallet` (`src/crystalWallet.ts`) ведёт счётчики веры и эфира только в локальной памяти и DOM. В `main.ts` создаются два экземпляра (`local` и `opponent`), но оба независимы: сетевой слой их не касается.

Снимок стола для мультиплеера (`captureBoardSnapshot` / `SerializedBoardStateV1` в `src/main.ts`, `src/multiplayer/boardState.ts`) синхронизирует юнитов, террейн, вихри, колоды богов, общие кубики и т.д., **но не кошельки кристаллов**.

## Цели

1. **Синхронизация:** у каждого игрока на экране отображаются **реальные** счётчики обоих участников (слоты `PlayerSlot` 0 и 1).
2. **Редактирование с любого клиента:** оба ряда кошельков остаются интерактивными; клики по «своему» или «чужому» ряду меняют счётчики **соответствующего слота** и видны оппоненту.
3. **Совместные правки:** при почти одновременных изменениях одного и того же счётчика итог строится как **сумма дельт** (каждый LMB = +1, RMB = −1 к типу кристалла), а не перезапись «последним полным JSON».
4. **Восстановление:** новый участник или реконнект получают актуальные счётчики из **полного снимка** стола.

## Не цели

- Изменение правил настолки (что означают кристаллы в игре).
- Отдельный UI для зрителей (если зрителю не показывают кошельки — без изменений; если показывают — достаточно тех же сообщений/снимка).

## Выбранный подход

**Дельты по WebSocket + полные счётчики в `syncBoard`.**

- **Дельты** — основной смысл «сложить клики»: маленькие сообщения с изменением (−1 / +1) по `(slot, crystalId)`.
- **Полный снимок** (`captureBoardSnapshot`) включает оба кошелька, чтобы применение `boardState` и реконнект восстанавливали состояние без потери типов кристаллов и абсолютных значений.

Чистый `syncBoard` без дельт не подходит: при одновременных правках двух клиентов целой снимок гонится и **не** даёт семантику суммирования кликов.

## Модель данных

- Два независимых набора: `crystalWallets['0']` и `crystalWallets['1']`.
- Формат: отображение `Record<crystalId, number>`, где `crystalId` ∈ `{ yellow, black, red, green, ether }` (как в `ALL_CRYSTALS` в `crystalWallet.ts`).
- Ограничения: как сейчас в UI — **0…99** на тип; при 0 тип **не хранится** в объекте (или хранится 0 — на усмотрение реализации, но UI должен совпадать с текущим «исчезает чип»).

## Привязка UI к слотам

- Известен `playerSlot` локального игрока (`0` или `1` из `joined`).
- Ряд **local** в вёрстке отображает кошелёк слота `playerSlot`.
- Ряд **opponent** — кошелёк слота `1 - playerSlot`.
- Клики по чипам и `[+]` на любом ряду вызывают дельты для **того слота, которому принадлежит этот ряд**, а не «всегда мой слот».

## Протокол (клиент ↔ сервер)

Добавить типы сообщений (имена ориентировочные; финально согласовать в `protocol.ts`):

**Клиент → сервер**

- `crystalWalletDelta`: `{ slot: PlayerSlot; crystalId: string; delta: number }`  
  - В норме `delta` ∈ `{ -1, +1 }`.  
  - Сервер валидирует `crystalId` по допустимому множеству и отбрасывает некорректное.

**Сервер → клиенты**

- Ретрансляция всем в комнате (включая отправителя при необходимости согласованного порядка), например `peerCrystalWalletDelta` с тем же полезным грузом и опционально `fromId` для отладки.

Парсинг в `parseClientMessage` и обработка в `server/roomServer.ts` по аналогии с `pointer` / `tableDrag` (без записи в `room.boardState` обязательно для дельт — см. ниже).

## Снимок стола

Расширить `SerializedBoardStateV1` (и валидацию `isSerializedBoardStateV1`) полем:

- `crystalWallets?: { '0': Record<string, number>; '1': Record<string, number> }`  
  - Для обратной совместимости поле опционально; при отсутствии трактовать как пустые кошельки.

`captureBoardSnapshot` заполняет его из текущей модели; `applyBoardSnapshot` восстанавливает оба кошелька и обновляет DOM виджетов.

После **локального** изменения кошелька вызывать `notifyBoardEditLocal()` (как для других правок стола), чтобы периодический push подхватил полный JSON.

## Поведение клиента

1. **Исходящая дельта:** по LMB/RMB и при добавлении типа через `[+]` формируется дельта для целевого слота; в мультиплеере отправляется на сервер. Локально UI обновляется сразу (оптимистично).
2. **Входящая дельта (от пира):** применить к модели соответствующего слота и обновить только этот виджет; **не** ретранслировать повторно.
3. **Входящий полный `boardState`:** применить кристаллы из снимка как часть `applyBoardSnapshot` (источник истины после реконнекта или если рассинхрон).
4. **Соло / не в комнате:** дельты не шлём; состояние только локально (можно хранить в той же структуре для единообразия).

## Крайние случаи

- **Порядок дельт:** при одинаковом порядке доставки у всех клиентов сумма дельт совпадает. Один WebSocket на клиент к серверу сохраняет порядок исходящих; сервер должен рассылать дельты так, чтобы пиры получали согласованную последовательность (достаточно последовательной обработки на сервере).
- **Снимок vs дельты:** теоретически устаревший `boardState` может перезаписать счётчики после серии дельт; снижается частым включением кошельков в `capture` и тем, что дельты тоже двигают модель. При расхождении после реконнекта **побеждает последний применённый полный снимок** — зафиксировать в реализации как приемлемое для игры в комнате.
- **Защита от читов** не входит в объём (доверенные клиенты).

## Файлы (ожидаемо)

- `src/crystalWallet.ts` — разделение «модель + отображение», привязка к слоту, колбэки дельт / внешнее обновление.
- `src/main.ts` — хранение двух кошельков в общей модели, создание виджетов, wiring с `playerSlot`, `capture` / `apply`, вызов `notifyBoardEditLocal`.
- `src/multiplayer/boardState.ts` — типы и валидация снимка.
- `src/multiplayer/protocol.ts` — новые типы сообщений и парсер.
- `src/multiplayer/roomClient.ts` / `src/multiplayer/session.ts` — диспатч входящих дельт.
- `server/roomServer.ts` — ретрансляция `crystalWalletDelta`.

## Критерии готовности

- В комнате с двумя игроками изменения кристаллов на любом из двух рядов у любого клиента отображаются у другого с задержкой не хуже остального MP-UI.
- Одновременные клики по одному счётчику с двух клиентов дают сумму изменений (в пределах 0…99), а не «кто последний прислал снимок — тот и прав».
- После перезагрузки страницы у присоединившегося игрока кошельки соответствуют последнему снимку стола из комнаты.
- В одиночной игре поведение кошелька не ломается.
