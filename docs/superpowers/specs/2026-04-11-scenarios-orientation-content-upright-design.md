# Сценарии: вертикальное поле без поворота контента

**Дата:** 2026-04-11  
**Статус:** утверждено пользователем для фиксации в спецификации

## Контекст

После внедрения сценариев `boardOrientation` (`horizontal|vertical`) в текущем runtime-поведении вертикальный сценарий фактически разворачивает не только поле, но и визуальное восприятие контента: карты богов, юниты, слепая зона и другие элементы смотрятся под общим поворотом.

Желаемое поведение:

- вертикальный сценарий должен менять восприятие поля;
- контент должен оставаться читаемым и ориентированным так же, как в привычном режиме;
- в мультиплеере сохраняется текущая seat-логика ориентации контента (не зависит от `vertical`/`horizontal`).

## Цели

1. Разделить поворот поля и поворот контента на независимые слои.
2. Сделать `boardOrientation` влияющим только на поле (геометрия/подложка/сетка).
3. Сохранить seat-based поведение для карт/юнитов/слепой зоны независимо от сценарной ориентации.
4. Избежать регрессий в hit-test, drag/drop, и синхронизации в MP.

## Не цели

- Изменение формата `ScenarioDocument` и отказ от `boardOrientation`.
- Перепроектирование всей камеры или переписывание всех рендер-пайплайнов.
- Изменение существующей seat-модели в мультиплеере.

## Выбранный подход

Подход: **разделение rotation на field-layer и content-layer**.

Вместо одной “общей” эффективной ротации вводятся две независимые вычисляемые величины:

- `effectiveFieldRotationDeg()` — для поля и его мировых преобразований.
- `effectiveContentRotationDeg()` — для читаемого контента (карты/юниты/слепая зона), где источником остаётся seat.

`boardOrientation: vertical` влияет только на `effectiveFieldRotationDeg()`.

## Функциональная спецификация

### Инварианты

1. При переключении `horizontal`/`vertical` контент не должен получать дополнительный поворот от сценарной ориентации.
2. Seat-коррекция в MP продолжает работать как раньше и применяется только в content-layer.
3. В `horizontal` и `vertical` сценариях hit-test и drag/drop остаются корректными и предсказуемыми, без регрессии относительно baseline-поведения в `horizontal`.
4. Применение сценария остаётся атомарным: валидировать -> применить snapshot -> применить orientation.

### Семантика слоёв

- **Field-layer**:
  - сетка, подложка, world-space представление поля;
  - преобразование экран<->мир, завязанное на поле.
- **Content-layer**:
  - ориентация юнитов, карт богов, слепой зоны и связанных “читаемых” элементов;
  - опирается на seat, а не на `boardOrientation`.

### Композиция трансформаций (нормативно)

1. Позиции сущностей в world-space (логические координаты модели) не меняются из-за `vertical`/`horizontal`.
2. `boardOrientation` влияет только на field-transform:
   - сетка;
   - подложка;
   - визуальная ориентация поля как поверхности.
3. Content-transform вычисляется отдельно и использует только seat-коррекцию (и существующие правила контента), без добавки угла от `boardOrientation`.
4. В vertical-сценарии `boardOrientation` не должен прибавляться к углам отображения юнитов, карт богов, слепой зоны и связанных overlays.
5. Hit-test/drag/drop используют согласованную модель world-space; сценарная ориентация поля не должна приводить к двойному повороту логики выбора/перетаскивания.

## Архитектурные изменения

### `src/main.ts`

- Разделить текущую модель эффективной ротации на:
  - `effectiveFieldRotationDeg()`;
  - `effectiveContentRotationDeg()`.
- `scenarioBoardOrientation` использовать только в field-layer.
- Перепривязать участки кода, где сейчас применяется общий поворот, к корректному слою.

### Рендер и связанные подсистемы

- Проверить точки использования rotation для:
  - карточек/юнитов;
  - слепой зоны;
  - health/effect overlays;
  - DOM-элементов, привязанных к world-space.
- Заменить зависимости от “общей” ротации на field/content вариант по назначению.

### Multiplayer и snapshot

- `boardOrientation` продолжает синкаться в snapshot как часть состояния сценария.
- Интерпретация на клиенте:
  - orientation -> field-layer;
  - seat -> content-layer.

## Data Flow

1. Пользователь применяет сценарий.
2. Документ валидируется.
3. Применяется snapshot состояния.
4. Применяется `boardOrientation` в field-layer.
5. Content-layer остаётся seat-driven.
6. Изменение распространяется через существующий MP-синк.

## Риски

1. Скрытые зависимости от старой “общей ротации” в отдельных подсистемах.
2. Несогласованность rotation в hit-test и отрисовке при частичной миграции.
3. Порядок применения orientation после snapshot может давать кратковременный визуальный “рывок”.

## Меры снижения рисков

- Централизовать API ротаций (два явных метода вместо одного).
- Выполнить поиск всех usage старого rotation-пути и классифицировать по слоям.
- Зафиксировать smoke-набор ручных проверок по ориентациям и MP.

## Тестирование

### Unit / Logic

- Проверка вычислений `effectiveFieldRotationDeg()` и `effectiveContentRotationDeg()` для сочетаний:
  - horizontal + seat0/seat1;
  - vertical + seat0/seat1.
- Проверка, что `boardOrientation` не влияет на content rotation.

### Integration

- Применение horizontal/vertical сценариев:
  - поле меняет ориентацию;
  - карточки/юниты/слепая зона остаются в ожидаемом читаемом виде.
- Hit-test и drag/drop на вертикальном сценарии не регрессируют.
- Health/effect overlays сохраняют читаемую ориентацию контента и не получают лишний поворот от `boardOrientation`.

### Multiplayer smoke

- Клиент A применяет vertical сценарий.
- Клиент B видит ту же ориентацию поля.
- Контент у каждого клиента ориентирован по seat-правилам, а не по “общему +90”.

## DoD

1. `vertical` меняет только field-layer.
2. Карты, юниты и слепая зона сохраняют читаемую ориентацию, зависящую только от seat.
3. Применение сценария и MP-синк не регрессируют.
4. Health/effect overlays не получают лишний поворот от `boardOrientation`.
5. Пройдены manual smoke тесты для solo и MP.
