# Редактирование официальных сценариев с мгновенной публикацией

**Дата:** 2026-04-12  
**Статус:** утверждено пользователем в brainstorming-сессии

## Контекст

Существующая система сценариев уже поддерживает:

- официальный каталог сценариев;
- пользовательские сценарии в `localStorage`;
- применение сценария как полного `snapshot`;
- редактирование пользовательских сценариев.

Новая задача: добавить редактирование **официальных** сценариев из клиента, без ролевой модели в v1.

Этот документ расширяет предыдущее ограничение из `2026-04-11-scenarios-system-design.md`, где серверная библиотека была out of scope.

## Подтвержденные требования

1. Любой пользователь может редактировать официальный сценарий (без прав доступа в v1).
2. Редактирование официального сценария влияет на всех пользователей.
3. Редактируются:
   - `meta.name`,
   - `meta.description`,
   - `meta.tags`,
   - `meta.difficulty`,
   - расположение элементов на поле (через новый `snapshot`).
4. Публикация выполняется сразу по `Сохранить` (без отдельного шага publish).
5. Конкуренция правок в v1: **last write wins**.
6. Доставка изменений всем пользователям: встроенная серверная публикация из клиента.

## Рассмотренные подходы

### A) Прямая серверная перезапись official-документа (выбрано)

Клиент отправляет полный обновленный `ScenarioDocument` на сервер, сервер перезаписывает официальный сценарий и рассылает событие обновления каталога.

### B) Patch-модель поверх official

Сохранять дельту относительно базового сценария и собирать итог при чтении.

### C) Полная версионная история official

Каждое сохранение создает новую версию, одна версия помечается активной.

### Почему выбран A

- минимальная сложность внедрения и UX без лишних шагов;
- точно соответствует требованию "сохранил -> увидели все";
- не требует сложной merge/patch логики в v1.

## UX-флоу

1. Во вкладке `Официальные` у карточки доступны `Применить` и `Редактировать`.
2. По `Редактировать` открывается режим правки:
   - поля `name`, `description`, `tags`, `difficulty`;
   - возможность изменить раскладку на поле.
3. Пользователь меняет раскладку прямо на столе.
4. По `Сохранить` клиент:
   - собирает новый `snapshot` из текущего стола;
   - формирует полный `ScenarioDocument`;
   - отправляет его на сервер.
5. Сервер сохраняет правку и публикует событие обновления official-каталога.
6. Все клиенты обновляют список официальных сценариев без перезагрузки.

## Архитектура

## Клиент

- Добавить editor-session для official-сценариев:
  - хранение `scenarioId`, исходного документа и черновика метаданных;
  - расчет dirty-state;
  - отмена без публикации.
- На сохранении:
  - `captureBoardSnapshot()`;
  - включение текущей `boardOrientation`;
  - `PUT` обновленного `ScenarioDocument` на сервер.
- После успеха:
  - обновить локальный кэш official;
  - показать toast об успешном обновлении.
- Если во время открытого редактора пришло внешнее обновление этого же `scenarioId`:
  - активная форма не сбрасывается;
  - при следующем `Сохранить` показывается confirm: "Сценарий уже изменился другим пользователем. Продолжить и перезаписать?";
  - при подтверждении выполняется обычный LWW-save.

## Сервер

- Endpoint: `PUT /api/scenarios/official/:id`.
- Read endpoints:
  - `GET /api/scenarios/official` -> `{ scenarios: ScenarioDocument[]; catalogUpdatedAt: string }`;
  - `GET /api/scenarios/official/:id` -> `{ scenario: ScenarioDocument }`.
- Валидация:
  - `params.id === body.id`;
  - `kind === "official"`;
  - `version === 1`;
  - `snapshot` валиден как `SerializedBoardStateV1`.
- Сохранение:
  - перезаписать официальный документ (LWW);
  - проставить `meta.updatedAt = now`;
  - проставить `meta.author` из контекста сессии/клиента (если доступен), иначе сохранить текущее значение.
- Публикация:
  - broadcast по существующему websocket-каналу события:
    - `type: "official_scenarios_updated"`
    - `catalogUpdatedAt: string`
    - `changedIds: string[]`.

## Realtime-контракт и восстановление

- Получив `official_scenarios_updated`, клиент выполняет `GET /api/scenarios/official` и целиком рефрешит каталог.
- Если клиент пропустил событие (reconnect / вкладка в фоне), на восстановлении websocket-сессии он также делает `GET /api/scenarios/official`.
- Если websocket недоступен, клиент использует деградацию: polling `GET /api/scenarios/official` раз в 30 секунд.

## Хранение official-каталога

- Источник истины переносится на сервер.
- Клиент получает official-сценарии по API и обновляет их по broadcast-событиям.
- Статические JSON-файлы используются только как seed на первом запуске сервера:
  1. если серверное хранилище пустое, импортируются `src/scenarios/data/official/*.json`;
  2. если хранилище уже заполнено, seed повторно не выполняется;
  3. runtime чтение всегда идет из серверного хранилища.

## Безопасность и эксплуатационные рамки v1

- Несмотря на отсутствие ролей, endpoint редактирования включается только при `SCENARIOS_OFFICIAL_EDIT_ENABLED=true`.
- Для публичных окружений флаг по умолчанию выключен.
- Рекомендованный режим v1: внутренний/доверенный контур (LAN, VPN или закрытый стенд).
- Базовый rate limit на update endpoint (например, 20 запросов в минуту на IP) обязателен.

## Data flow

### Обновление официального сценария

1. Открыть сценарий в редакторе.
2. Изменить метаданные и/или раскладку на поле.
3. Нажать `Сохранить`.
4. Клиент отправляет полный документ на сервер.
5. Сервер валидирует и сохраняет.
6. Сервер рассылает событие обновления official-каталога.
7. Клиенты обновляют карточки official.

### Важно про активные партии

Изменение official-каталога не должно автоматически заменять текущий стол в существующих сессиях.  
Новый вариант сценария применяется к столу только по явному `Применить`.

## Обработка ошибок и ограничения v1

- Перед сохранением показать явное предупреждение: изменение повлияет на всех.
- Ошибки API:
  - `400` — невалидный документ;
  - `404` — сценарий не найден;
  - `409` — update endpoint отключен флагом среды;
  - `413` — payload слишком большой;
  - `500`/network — сохранить как неуспешно, дать retry.
- При неуспешном сохранении публикации не происходит.
- В v1 нет блокировки редактирования, нет merge UI, нет прав доступа.

## Тестирование

## Unit (клиент)

- сборка корректного `ScenarioDocument` из editor-state;
- dirty-state для метаданных и раскладки;
- поведение при внешнем обновлении того же сценария во время открытого редактора;
- обработка ошибок API и retry-сценарии.

## Unit (сервер)

- валидация payload и route-id;
- LWW-поведение при последовательных апдейтах;
- отказ при `SCENARIOS_OFFICIAL_EDIT_ENABLED=false` (409);
- отказ при невалидном `snapshot`;
- отказ при превышении размера payload;
- корректное обновление `updatedAt` и сохранение `author`.

## Integration

- пользователь A сохраняет official-сценарий, пользователь B видит обновление каталога без reload;
- изменение official не перезаписывает текущий стол у B автоматически;
- после `Применить` у B загружается новая раскладка.
- если B редактировал тот же сценарий и получил внешнее обновление, при сохранении появляется confirm LWW.

## Multiplayer smoke

- в комнате A публикует правку official;
- B получает обновление каталога;
- B применяет сценарий, и клиенты сходятся по состоянию через текущий sync pipeline.

## Scope v1 (минимальный)

1. Серверный endpoint `PUT /api/scenarios/official/:id` + broadcast.
2. Клиентская загрузка official с сервера + подписка на обновления.
3. UI-режим редактирования official (`Редактировать`, `Сохранить`, `Отмена`).
4. Публикация полного `ScenarioDocument` на `Сохранить`.
5. Guardrails и тесты.

## Out of scope

- Роли и права доступа.
- Draft/publish двухфазный процесс.
- Блокировка "захвачено в редактирование".
- Автоматический merge конфликтующих правок.
- Полная история версий и откаты через UI.
