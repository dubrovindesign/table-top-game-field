# Пинг намерения: временная анимированная стрелка

**Дата:** 2026-04-11  
**Статус:** утверждено пользователем для планирования реализации

## Контекст

Во время матча игроку нужно быстро показать намерение ("смотри сюда"), не ломая текущие боевые взаимодействия.  
В текущем управлении:

- ПКМ уже занят контекстными меню (вихри, маркеры эффектов и т.д.);
- ЛКМ/двойной ЛКМ участвует в выборе, драге и открытии карточек миниатюр;
- решение должно одинаково работать на ПК и планшете.

## Цели

1. Добавить "пинг намерения" в виде короткой анимированной стрелки в точке на столе.
2. Не конфликтовать с существующими действиями ЛКМ/ПКМ вне режима пинга.
3. Поддержать единый UX для ПК и планшета.
4. Синхронизировать пинг в мультиплеере как transient-событие.

## Не цели

- Рисование протяженных стрелок "из точки в точку".
- Привязка к юнитам (source/target) в первой версии.
- Сохранение пингов в снапшоте стола.

## Выбранный подход

Подход 1: **Unified Ping Mode**.

- Планшет: tap-to-arm по плавающей кнопке `Ping` (single-shot) + следующий тап в точку на поле.
- ПК: та же плавающая кнопка в режиме удержания + быстрый шорткат `Space + ЛКМ`.
- Визуал: фиксированная по ориентации (вверх) анимированная стрелка, исчезающая по TTL.

## UX и Input Model

Вводится состояние `pingIntentArmed`.

- `pingIntentArmed = true`, если:
  - на ПК удерживается плавающая кнопка `Ping`, или
  - на ПК удерживается `Space`.
- На сенсорных устройствах `Ping` работает как tap-to-arm: один тап по кнопке включает `pingIntentArmed` до первого валидного тапа по полю (single-shot).
- При `pingIntentArmed = true` следующий `ЛКМ/тап` по полю:
  - не запускает обычный выбор/драг/двойной клик;
  - вызывает `spawnPing(worldX, worldY)`;
  - сбрасывает `pingIntentArmed` (single-shot).
- Отпускание `Space` или кнопки `Ping` на ПК до валидного клика по полю сбрасывает `pingIntentArmed` без создания пинга.
- ПКМ и существующие context menu остаются без изменений.
- Пинг не армится, если фокус находится в `input`, `textarea`, `select` или `contenteditable`.

## Визуал и анимация

Тип эффекта: `PingMarker`.

- Позиция: world coordinates точки клика.
- Направление: фиксированно вверх.
- Рендер: в `renderer.ts` на canvas в world space (не DOM-оверлей), чтобы поведение автоматически соответствовало зуму и камере.
- Жизненный цикл: `PING_TTL_MS = 1200` (константа, настраиваемая).
- Тайминг:
  - 0-150 ms: scale `0.85 -> 1.0`, alpha `0 -> 1`;
  - 150-900 ms: стабильный показ;
  - 900-1200 ms: alpha `1 -> 0`.
- Несколько пингов могут существовать одновременно и затухают независимо.

## Мультиплеер

Пинги передаются отдельным transient-сообщением.

- Клиент -> сервер: `pingIntent` с `boardX`, `boardY`.
- Сервер -> клиенты: `peerPingIntent` с `fromId`, `boardX`, `boardY`.
- `boardX`/`boardY` используют ту же board/world систему координат, что и текущий live-pointer и hit-тесты рендера.
- Отправка только при фактическом пинге (не потоково).
- Anti-spam:
  - клиентский cooldown `PING_CLIENT_COOLDOWN_MS = 300`;
  - при необходимости server-side rate limit per peer.
- Пинги не включаются в `boardState` snapshot.
- Пинги рассылаются всем участникам комнаты (игроки и зрители с активным подключением).

## Edge cases

- Клик/тап по UI-оверлеям и панелям не создает пинг.
- Потеря фокуса окна сбрасывает armed-состояние.
- При открытых модальных вводах `Space` не должен армить пинг.
- ПК с одной мышью: основной быстрый путь это `Space + ЛКМ`; плавающая кнопка `Ping` на ПК рассчитана прежде всего на сценарии touch/pen или альтернативный стиль управления.
- В armed-режиме ПКМ/средняя кнопка/жест "назад" не создают пинг и обрабатываются стандартно.
- Вне armed-состояния все текущие действия ЛКМ/ПКМ работают как раньше.

## Критерии готовности (DoD)

1. На планшете: tap-to-arm по `Ping` + следующий тап по полю показывает стрелку локально.
2. На ПК: плавающая кнопка и `Space + ЛКМ` делают то же самое.
3. В мультиплеере второй игрок/зритель видит тот же пинг визуально синхронно с локальным эффектом.
4. Контекстные меню по ПКМ и даблклик-карточка не регрессируют вне ping-режима.
5. Пинги самоуничтожаются по TTL и не сохраняются в snapshot.

## Предлагаемые изменения по модулям

- `src/main.ts`
  - состояние `pingIntentArmed`, обработка `Space`, перехват single-shot клика/тапа в режиме пинга;
  - интеграция плавающей кнопки `Ping` в UI;
  - вызов `spawnPing` и отправка `pingIntent` в MP-транспорт.
- `src/renderer.ts`
  - хранение/отрисовка списка активных `PingMarker`;
  - анимация по `performance.now()` и удаление по TTL.
- `src/multiplayer/protocol.ts`
  - новые типы сообщений `pingIntent` / `peerPingIntent`.
- `src/multiplayer/session.ts`
  - отправка `pingIntent`, прием `peerPingIntent`, прокидка в рендерер.
- `server/roomServer.ts`
  - прозрачная ретрансляция `pingIntent` в комнате как transient-события.

## Риски

- Перехват клика в armed-режиме может затронуть существующие drag/click сценарии.
- Неверная фильтрация таргета (canvas vs UI) может создавать ложные пинги.
- При высоком RTT нужны мягкие допуски по ожидаемой задержке отображения.

## Ручной тест-план

1. ПК: `Space + ЛКМ` по полю -> стрелка появляется и исчезает по TTL.
2. ПК: плавающая `Ping` + ЛКМ по полю -> тот же результат.
3. Планшет: tap по `Ping` (arm) + следующий тап по полю -> тот же результат.
4. ПКМ по юниту/вихрю открывает прежние меню.
5. Двойной ЛКМ по миниатюре вне ping-режима открывает карточку как раньше.
6. В комнате из 2 клиентов оба видят пинг; flood-клики не вызывают чрезмерной нагрузки.
7. ПК: отпустить `Space` до клика по полю -> пинг не создается.
8. Фокус в поле ввода (chat/input) + `Space` -> режим пинга не активируется.
