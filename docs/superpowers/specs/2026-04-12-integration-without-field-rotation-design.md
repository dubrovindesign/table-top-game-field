# Интеграция веток в одну версию без поворота поля

**Дата:** 2026-04-12  
**Статус:** утверждено пользователем для фиксации в спецификации

## Контекст

Текущее состояние репозитория усложнилось из-за нескольких worktree/веток с незакоммиченными изменениями.  
Цель: собрать все последние полезные изменения (сценарии, пинги, курсор и прочие актуальные правки) в одну рабочую версию, но исключить функционал поворота поля.

Ключевое ограничение:

- нужно максимально сохранить изменения;
- убрать только behavior, связанный с field rotation;
- минимизировать риск потери/поломки из-за конфликтов.

## Цели

1. Свести разрозненные изменения в одну интеграционную ветку.
2. Сохранить “максимум” правок из актуальных источников.
3. Удалить только поведение поворота поля.
4. Обеспечить пошаговую валидацию после каждого интеграционного слоя.

## Не цели

- Полная архитектурная переработка сценарной системы.
- Рефакторинг, не относящийся к интеграции и отключению field rotation.
- Изменение продуктовых требований по пингам/курсору/прочим фичам.

## Нормативная граница field rotation

Для этой интеграции под **field rotation behavior** понимается только runtime-поворот поля как визуальной/геометрической поверхности (поворот, влияющий на восприятие и ориентацию поля).

Что убирается:

- применение сценарной ориентации как активного runtime-поворота поля;
- связанная с этим нежелательная визуальная ротация в итоговом UX.

Что сохраняется:

- сценарная подсистема, пинги, курсор и прочие фичи;
- структура данных сценариев и совместимость импорт/экспорт/snapshot;
- существующие несвязанные product-behavior изменения.

Важно: в рамках этого документа не выполняется изменение/очистка формата сценарных JSON, если это не критично для отключения runtime-поворота поля.

## Выбранный подход

Подход: **гибридная послойная интеграция (3 слоя)**.

Причины выбора:

- безопаснее “большого комка” (проще локализовать регрессии);
- быстрее и практичнее сверхмелкой интеграции;
- позволяет сохранить максимум правок и вырезать только целевой behavior.

## Интеграционная ветка и инварианты

Создаётся новая ветка: `integration/stable-all` от актуального `main`.

Инварианты:

1. Ветка является единственной “сборочной” поверхностью для финальной версии.
2. Старые worktree/ветки до финала не удаляются (роль страховки).
3. Каждая группа изменений переносится атомарным слоем.
4. Единственное целевое исключение в итоге — field rotation behavior.

## Слойная стратегия

### Layer 1 — Baseline Feature Pack

Переносим актуальные правки, не относящиеся к сценарной подсистеме, чтобы получить рабочий baseline.

Ожидаемый результат:

- пинги, курсор и прочие недавние фичи работают как в текущем рабочем состоянии;
- базовый pipeline `build/preview:mp` стабилен.

### Layer 2 — Scenario Pack (maximal)

Переносим максимально полный сценарный пакет:

- `src/scenarios/**`;
- все интеграционные изменения в `main`, `appMoreMenu`, `style`, `boardState` и связанные точки.

Ожидаемый результат:

- функционал сценариев доступен целиком (UI, хранение, импорт/экспорт, применение, MP).

### Правило для пересекающихся файлов

Файлы, которые пересекаются между слоями (например `main.ts`, `renderer.ts`, `style.css`), переносятся по единому порядку:

1. сначала фиксируется baseline-версия файла после Layer 1;
2. затем добавляется сценарный пакет (Layer 2) целиком для этого файла;
3. в Layer 3 выполняется только целевой remove-field-rotation проход без дополнительных “улучшений”.

Запрещено одновременно менять семантику и “чистить” код при конфликт-резолве: конфликт должен решаться минимально необходимым способом.

### Layer 3 — Remove Field Rotation Behavior

Точечно удаляется только поведение поворота поля:

- исключается влияние сценарной ориентации как field-rotation behavior;
- остальные сценарные и несценарные функции сохраняются.

Ожидаемый результат:

- сценарии, пинги, курсор и остальное продолжают работать;
- поворот поля как нежелательный behavior отсутствует.

## Data Flow интеграции

1. Подготовка интеграционной ветки.
2. Применение Layer 1.
3. Проверка gate.
4. Применение Layer 2.
5. Проверка gate.
6. Применение Layer 3.
7. Финальный gate и выпуск итоговой ветки.

## Safety Gates (после каждого слоя)

### Gate L1 (после Layer 1)

1. `npm run build` — обязателен успех.
2. `npm run preview:mp` — процесс стартует и остается стабильным.
3. Smoke:
   - пинги работают;
   - курсор/инпут без регрессий.

### Gate L2 (после Layer 2)

1. `npm run build` — обязателен успех.
2. `npm run preview:mp` — процесс стартует и остается стабильным.
3. Smoke:
   - пинги и курсор без регрессий;
   - сценарии открываются/применяются;
   - импорт/экспорт и хранение сценариев работают.

### Gate L3 (после Layer 3)

1. `npm run build` — обязателен успех.
2. `npm run preview:mp` — процесс стартует и остается стабильным.
3. Smoke:
   - пинги, курсор, сценарии работают;
   - field rotation behavior отсутствует;
   - в MP нет регрессий по применению сценариев.

Если gate не проходит:

- слой не считается завершенным;
- исправления выполняются до перехода к следующему слою.

## Риски

1. Конфликты из-за пересечения правок в `main.ts`/`renderer.ts`/`style.css`.
2. Частичный перенос может незаметно опустить критичный кусок логики.
3. Слишком агрессивное удаление rotation-зависимостей может повредить смежный runtime.

## Меры снижения рисков

- Перед интеграцией фиксировать текущие состояния (WIP-коммиты/бэкап-ветки).
- Делать проверку после каждого слоя, не в конце всего процесса.
- Удалять только подтвержденные field-rotation участки, без побочных рефакторингов.
- Для каждого слоя вести инвентаризацию источников (ветка/коммиты/файлы) и сверять фактический перенос перед переходом к следующему слою.

## Тестирование

### Техническое

- `npm run build` на каждом слое.
- `preview:mp` smoke после каждого слоя.

### Функциональное

- Проверка сценариев (загрузка/применение).
- Проверка пингов и интерактивных элементов.
- Проверка отсутствия нежелательного поворота поля в итоге.

## DoD

1. Все целевые изменения объединены в одной интеграционной ветке.
2. Сценарии, пинги, курсор и прочие актуальные фичи сохранены.
3. Field rotation behavior удален.
4. Все layer gates пройдены.
5. Итоговая ветка готова к merge в `main` или к работе как основной источник.
