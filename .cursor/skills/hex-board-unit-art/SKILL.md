# Hex board — арт к уже заведённым юнитам

## Цель

Пользователь **уже** имеет записи в `src/catalog/units/<id>.json`. Нужно **добавить или заменить** изображения карточки и миниатюры, не пересобирая статы с нуля.

Канон доменов, имён и структуры каталога — **[hex-board-canon](../hex-board-canon/SKILL.md)**.

## Когда использовать этот скилл vs `hex-board-faction-sheet`

| Ситуация | Скилл |
|----------|--------|
| Новая фракция / полная сетка: сетка, статы, хотспоты, лидер с нуля | [hex-board-faction-sheet](../hex-board-faction-sheet/SKILL.md) |
| Юниты в JSON уже есть; не хватает или устарел **арт** (лицо, оборот, миниатюра) | **этот скилл** |

## Входы (разветвление)

1. **Спрайт-листы** — два листа с сеткой карточек (лицо и оборот), как в KoW/Tornscape. Имена файлов могут быть любыми.
2. **Отдельные файлы на юнит** — для части юнитов приходят пары «фронт / бэк» (и при необходимости отдельный файл миниатюры).

Можно **смешивать** в одной задаче: часть юнитов из сетки, часть — из отдельных файлов, если пользователь так явно разделил вход.

## Определение «лицо» и «оборот»

**Не по имени файла.** Смотреть содержимое:

- **Лицо** — портрет, баннер с именем, игровая лицевая вёрстка.
- **Оборот** — текст правил, единый шаблон оборота.

То же правило, что в [hex-board-faction-sheet §1](../hex-board-faction-sheet/SKILL.md).

## Сопоставление имён с каталогом

1. **Источник имени для матчинга** — строка **`card.name`** в уже существующем `src/catalog/units/<id>.json` (отображаемое имя в UI и на карте).
2. **Считать имя с арта** с лицевой стороны (и при необходимости сверить с оборотом: на обороте часто тот же юнит / тот же заголовок).
3. **Сопоставление**:
   - в первую очередь **точное** совпадение с `card.name` после нормализации пробелов (`trim`, схлопывание повторных пробелов);
   - если нет совпадения — **поиск** по всем `units/*.json` (grep / чтение списка): подстрока, отличие в кавычках/тире, опечатки;
   - при **нескольких кандидатах** — перечислить пользователю и **не угадывать** без подтверждения;
   - целевой ключ юнита — поле **`id`** файла (стабильный slug), не путать с именем файла при странных символах.

Если имя на карте **сильно расходится** с любым `card.name` — зафиксировать расхождение и спросить: править `card.name` в JSON (осознанно, по канону) или считать это другим юнитом.

## Куда класть файлы и что править в JSON

Каталог ассетов на диске: **`public/catalog-units/<unit_id>/`**.

Типичный набор (как в репозитории):

| Файл | Назначение |
|------|------------|
| `face.jpg` | Лицевая карточка (кроп ячейки или одиночный файл) |
| `image.jpg` | То, на что ссылается **`card.sprite`** — часто склейка лица и оборота по вертикали для скролла карты в клиенте |
| `miniature.jpg` | Токен на столе — **`card.miniatureSprite`** |

В **`src/catalog/units/<id>.json`** обновить минимум:

- `"sprite": "/catalog-units/<id>/image.jpg"` (или актуальный путь под выбранный пайплайн)
- `"miniatureSprite": "/catalog-units/<id>/miniature.jpg"`

Пути — от корня `public`, с ведущим `/`.

**Хотспоты** (`src/catalog/hotspots/<id>.json`): поле `image` обычно указывает на тот же `image.jpg`, что и карточка. При смене размеров/пропорций склейки обновить **`scrollLayout`** (`faceH`, `totalH`) и при необходимости пересчитать нормализованные `regions` — см. существующие скрипты `scripts/build-*-scroll-cards.mjs` и [reference.md](reference.md).

## Ветка A: спрайт-листы

1. Взять геометрию сетки: размеры листа, число колонок/рядов, правило для неполного последнего ряда — как в [hex-board-faction-sheet §2–3](../hex-board-faction-sheet/SKILL.md).
2. Нарезать ячейки (временная папка или скрипт по образцу `scripts/split-*-spritesheet.mjs`).
3. Для **каждой** ячейки: прочитать имя → сопоставить с `card.name` → положить `face.jpg` (и при отдельном шаге оборот) в `public/catalog-units/<id>/`.
4. Склеить лицо + оборот в **`image.jpg`**, если клиент ждёт вертикальный скролл — по тому же принципу, что в `scripts/build-*-scroll-cards.mjs` / `ingest-*` в репозитории.
5. Миниатюра: отдельный слой на листе, отдельный файл от пользователя, или кроп из лица — **уточнять по задаче**; сохранить как `miniature.jpg`.

## Ветка B: отдельные фронт и бэк по юнитам

1. Для каждой пары файлов: определить лицо/оборот (§ выше), прочитать имя с **лица**.
2. Сопоставить с юнитом по `card.name` (§ «Сопоставление»).
3. Записать в `public/catalog-units/<id>/`: `face.jpg`, оборот (например `back.jpg` или сразу участвует только в склейке — по принятому в проекте сценарию).
4. Собрать **`image.jpg`** (лицо + оборот), обновить JSON и при необходимости хотспоты/`scrollLayout`.
5. Добавить **`miniature.jpg`** из отдельного файла или из обозначенного источника.

## Ссылки на файлы

Если пользователь даёт **URL** — скачать в рабочую папку (например `.cursor/tmp/...`), затем обработать как локальные файлы. Не считать имя файла в URL истиной для матчинга; истина — текст на карточке и `card.name` в JSON.

## Проверка

- После изменений каталога: `npm run catalog:bundle` (или как в проекте для бандла) и **`npm run build`**.
- Превью: по **AGENTS.md** — сборка перед `vite preview`.

## Чеклист агента

- [ ] Лицо и оборот не перепутаны (по содержимому, не по имени файла).
- [ ] Каждый арт привязан к существующему `id`, матчинг через `card.name` проверен или согласован с пользователем.
- [ ] Обновлены `sprite` и `miniatureSprite`; при склейке — `image.jpg` и при необходимости хотспоты/`scrollLayout`.
- [ ] Сборка и бандл каталога проходят.
